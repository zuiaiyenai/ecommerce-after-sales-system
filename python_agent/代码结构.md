# Python 售后 Agent 代码结构

本文描述 `python_agent/after_sales_agent` 的当前生产结构、职责边界和依赖方向。历史目录 `api/`、`agents/`、`infra/`、`services/` 及根包兼容入口已退役，不应再被引用或恢复。

## 1. 系统边界

- Python Agent 负责 LangGraph 编排、LLM 推理、RAG、图片审核、工具规划、失败降级和人工转接建议。
- Java 负责订单、售后工单、聊天消息、审核结果、权限、事务和最终状态流转。
- Python 只通过 `integrations/java_tool_client.py` 调用 Java 内部接口，不直接写 MySQL 业务状态。
- MySQL 是售后业务事实来源；PostgreSQL/pgvector 只保存知识文档、分块、向量和检索元数据。
- Redis 只承担短期幂等、缓存和限流；Kafka 只承担异步事件投递。
- AI 输出是建议。正式审核必须经过确定性 Gate，并由 Java 再校验和落库。

## 3. 依赖方向

```text
interface
   ↓
agent → workflows / skills / application
            ↓
       tools / retrieval / providers / integrations
            ↓
       infrastructure / config / utils
```

约束：

1. `domain` 不得导入 LangGraph、HTTP 客户端、数据库驱动或其他技术框架。
2. `interface` 只做协议解析、调用用例和响应序列化，不承载售后决策。
3. `agent` 是唯一自主调度主体；已知 Kafka 审核事件直接调用正式审核 Skill。
4. `skills` 只保存业务能力说明和引用资料，不包含 Python 执行代码。
5. `tools` 只执行确定性动作，不拥有 LLM 推理或最终业务状态。
6. `application` 编排聊天、情绪和知识入库用例，不直写 MySQL。
7. 外部模型通过 `providers` 接入；业务系统调用通过 `integrations` 接入。
8. 新检索逻辑放入 `retrieval`，不再创建第二份 pgvector 实现。

## 4. 三条主链路

### 4.1 普通咨询与 Agentic RAG

```text
Java 网关
  → interface/http_server.py
  → interface/http_adapter.py
  → application/request_payload_adapter.py
  → agent/agent.py
  → agent/workflows/consultation.py
  → tools/registry.py
  → retrieval/pgvector_retriever.py
  → providers/llm_client.py
  → integrations/java_tool_client.py 持久化消息或转人工
```

对话只在可信知识足够时生成政策回答。检索基础设施失败、政策不可信或知识仍有缺口时，流程安全转人工。

### 4.2 LangGraph 售后对话图

`application/after_sales_workflow.py` 是历史对话兼容 Workflow。当前聊天入口由 `agent/agent.py` 调度 `agent/workflows/consultation.py`。模型不能绕过 `tools/registry.py` 直接执行业务写入。

### 4.3 Kafka 正式审核

```text
interface/kafka_adapter.py
  → agent/agent.py
  → agent/workflows/formal_review/graph.py
  → policy/evidence workflows
  → complex review synthesizer（仅复杂案例）
  → deterministic gate
  → submit_review / request_missing_evidence / submit_manual_review
  → integrations/java_tool_client.py
```

Kafka 消费以事件/审核请求为幂等键。只有处理成功或进入受控 DLQ 后才提交 offset；checkpoint 由 `infrastructure/review_checkpoint.py` 管理，不把长期业务状态放入 Redis。

## 5. Skill 与 Workflow 边界

- `after_sales_agent/skills/`：以 `SKILL.md` 为核心的触发条件、SOP、约束和引用资料。
- `after_sales_agent/agent/workflows/`：Skill 对应的 Python/LangGraph 执行实现。
- `agent/skill_registry.py`：启动时只扫描 frontmatter；命中场景后加载正文，进入具体步骤后加载 reference，并以完整 Skill 包生成内容哈希版本。

Skill 描述“做什么和遵守什么”，Workflow 实现“程序如何运行”。

## 6. RAG 与模型边界

- 标准检索链路：`text-embedding-v3 → pgvector/pg_trgm → RRF → qwen3-rerank`。
- `lexical_fallback_after_embedding_error` 表示 embedding 未正常工作，不等于知识库为空。
- `providers` 保留各模型的超时、重试条件和降级策略；共享的熔断、重试和并发控制原语位于 `infrastructure/resilience.py`。
- 查询改写只能补充自然语言查询，不能修改商家、品类、政策版本和业务时间等硬过滤条件。

## 7. 运行与验证

```powershell
cd python_agent
python -m after_sales_agent.interface.http_server
python -m pytest tests -q
python -m compileall -q after_sales_agent
```

Docker 与本机启动都应指向 `after_sales_agent.interface.http_server`。新增依赖必须同步写入 `requirements.txt`。
