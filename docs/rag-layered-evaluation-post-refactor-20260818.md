# 售后 Agent 分层 RAG 评测报告（架构收敛后）

评测日期：2026-08-18

## 1. 结论摘要

本轮已完成 Python Agent 同步与运行验证，并按“数据集质量 -> Retrieval -> Context -> Generation -> End-to-End”分层评测。

- 知识库 42 篇生效文档均已索引，共 42 个有效 Chunk，无未索引文档。
- 36 条本地评测集上，Rerank 模式 Recall@5 为 93.33%，MRR@10 为 100%，NDCG@5 为 94.60%，无答案误召回率为 0%。
- 最终上下文 Context Precision 为 91.67%，Context Recall 为 93.33%。
- 生成 Faithfulness 为 97.14%，完全忠实回答率为 86.67%；生成 p50/p95 为 2.24/3.95 秒。
- ANSWER/NO_ANSWER 路由 Accuracy 与 Macro-F1 均为 100%。该指标不是退款审批准确率。
- Java -> Python 健康链路在 100 请求、并发 10 下成功率 100%，吞吐 472.79 RPS，p95 35.44 ms。
- 真实咨询链路在并发 1 下无模型限流，4/4 完成链路执行，p50/p95 为 10.89/11.78 秒；并发 3 时 83.33% 请求因模型侧 429 进入 fallback，当前瓶颈是外部模型并发配额与退避策略。
- Kafka 审核消费者组 `python-after-sales-agent-review` 最终 LAG 为 0。

当前不能宣称“混合检索的关键词通道有效提升召回”：Keyword 模式正向 Recall@5 为 0%，当前正向召回主要来自 Dense，RRF 实际没有获得关键词侧增益。

## 2. 评测口径

数据集共 36 条：30 条有答案售后问题、6 条无答案或越权问题。数据由单人策划并标注，属于本地回归集，不是双人标注、冲突仲裁后的生产 Holdout。因此本报告指标可用于架构验证和优化对比，不能直接外推生产准确率。

本轮 Generation 评测绕过 Java 持久化，不产生业务写入。Faithfulness 使用 LLM-as-Judge，仍需人工抽检。业务 Accuracy/F1 只衡量是否应回答（ANSWER/NO_ANSWER），不衡量自动通过、补证、拒绝或退款金额是否正确。

## 4. Retrieval 检索层

| 模式 | Recall@5 | MRR@10 | NDCG@5 | HitRate@5 | 无答案 FPR | p50 | p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Dense | 97.78% | 100% | 98.44% | 100% | 50.00% | 316.82 ms | 455.24 ms |
| Keyword | 0% | 0% | 0% | 0% | 0% | 23.54 ms | 41.40 ms |
| RRF | 97.78% | 100% | 98.44% | 100% | 66.67% | 59.07 ms | 162.06 ms |
| Rerank | 93.33% | 100% | 94.60% | 100% | 0% | 208.10 ms | 278.10 ms |

所有模式的过滤越权率均为 0。Rerank 将所有正向问题的正确知识排到第一位，并把无答案误召回率压到 0%；但阈值裁掉了部分通用金标 Chunk，使集合 Recall 低于 Dense。

主要问题：

1. Keyword 对 30 条正向问题完全没有召回，需检查 `pg_trgm` 相似度阈值、中文分词/归一化、别名映射和查询字段。
2. Dense 对无答案问题的 FPR 为 50%，RRF 为 66.67%，说明不能在 Reranker/拒答门控前直接使用候选结果生成回答。
3. Rerank Recall@5 从 Dense 的 97.78% 降至 93.33%，应针对通用规则 Chunk 调整阈值或采用“专用规则保留 + 通用规则补充”的分层上下文策略。

## 5. Context 上下文层

| 指标 | 结果 |
| --- | ---: |
| Context Precision | 91.67% |
| Context Recall | 93.33% |
| 空上下文率（正向样本） | 0% |

Precision 较高，说明最终喂给模型的内容噪声有限。Recall 损失主要出现在需要“品类专用规则 + 通用质量规则”共同回答的复合问题，例如耳机无声、手机充电异常和手机黑屏。

## 6. Generation 生成层

| 指标 | 结果 |
| --- | ---: |
| Faithfulness | 97.14% |
| 完全忠实回答率 | 86.67% |
| Generation p50 | 2.24 s |
| Generation p95 | 3.95 s |

整体事实忠实度较高，但 4/30 个回答至少包含一条 Judge 判定为未被上下文直接支持的陈述。后续应把“流程性建议”和“知识事实声明”分开约束，并对时限、承诺、退款方式等高风险声明增加可引用证据检查。

## 7. End-to-End 业务层

### 7.1 离线路由质量

| 指标 | 结果 |
| --- | ---: |
| ANSWER/NO_ANSWER Accuracy | 100% |
| Macro-F1 | 100% |

该结果仅表示 36 条样本上回答/拒答路由正确，不能写成“售后审核准确率 100%”。正式审核业务还需要带订单、凭证和确定性 Gate 的独立金标集，分别统计自动通过、补证、转人工等类别的 Precision/Recall/F1。

### 7.2 HTTP 与真实咨询压测

| 场景 | 请求/并发 | HTTP 成功率 | 链路执行成功率 | Fallback | 吞吐 | p50 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 鉴权健康链路 | 100/10 | 100% | 100% | 0% | 472.79 RPS | 15.44 ms | 35.44 ms | 48.35 ms |
| 真实咨询顺序基线 | 4/1 | 100% | 100% | 0% | 0.09 RPS | 10.89 s | 11.78 s | 11.86 s |
| 真实咨询并发 | 12/3 | 100% | 16.67% | 83.33% | 1.07 RPS | 0.21 s | 10.67 s | 11.13 s |

并发场景中的 10 次 fallback 原因为外部模型 `429`。快速 fallback 拉低了总体 p50，因此不能把 0.21 秒解释为正常回答延迟；完整成功请求平均约 10.73 秒。

顺序基线虽然没有异常降级，但该无订单测试请求缺少可信品类/场景过滤上下文：初次检索为 `pgvector_relaxed_filters`，多查询改写后仍为 `multi_query_empty`，最终按 `knowledge_not_trusted` 安全转人工。因此这里的“链路执行成功”不等于“成功生成知识回答”。这也证明安全门控有效，但暴露了测试请求和在线场景元数据契约需要补齐。

未鉴权健康压测的 100 次请求全部返回 401，证明鉴权生效；该组仅是安全拒绝基线，不计入容量结论。

## 8. 优先改进项

1. 修复 Keyword 召回为 0 的问题，并单独验证关键词通道对 Dense 未命中样本的增量贡献。
2. 为真实聊天请求补齐稳定的 `merchant/category/scene/intent` 推导或显式上下文，避免无订单咨询直接进入宽松过滤后无可信命中。
3. 在模型调用前增加并发舱壁、请求队列和 429 指数退避；容量指标应同时报告 HTTP 成功、完整业务成功、fallback 和安全转人工。
4. 建立双人标注的生产 Holdout，覆盖相似政策、版本过期、跨商家越权、复合规则与无答案问题。
5. 为正式审核建立独立业务金标集，测 Gate 最终类别的 Accuracy/Precision/Recall/F1，并验证重复 Kafka 投递、崩溃接管和 Java 状态幂等。

## 9. 简历表述建议

可使用以下保守口径：

> 构建售后 RAG 分层评测体系，覆盖知识库完整性、Recall@K/MRR/NDCG、Context Precision/Recall、Faithfulness 及端到端降级率；在 36 条本地回归集上实现 Rerank Recall@5 93.33%、MRR@10 100%、Faithfulness 97.14%，并通过并发压测定位外部模型 429 为主要容量瓶颈，推动限流、退避与安全转人工治理。

正式简历若不说明“36 条本地回归集”，容易让指标显得失真；在建立生产 Holdout 后再替换为更有说服力的数据。
