# 5 分钟项目演示脚本

演示前准备：完整运行栈健康、微信开发者工具已打开、演示账号已有订单/售后/会话数据、Prometheus Targets 为 UP。

## 0:00–0:30 项目背景

**我说：**

> 这是一个电商售后智能客服系统。我把订单、售后工单、客服会话和评价作为 Java 业务内核，把 AI Agent、RAG 和图片理解作为可降级能力。目标是让 AI 提高处理效率，同时保证状态、权限和审计仍由确定性业务代码控制。

**我展示：** README 顶部和系统架构图。

**面试官应看到：** 项目边界清楚，业务系统与模型职责分离。

## 0:30–1:00 系统架构

**我说：**

> 小程序和客服端访问 Spring Boot。MySQL 保存业务事实，Redis 处理限流和消费幂等，Kafka 解耦售后正式审核。Python AfterSalesAgent 通过 Java 内部 API 获取可信上下文，再访问 pgvector、Ollama 和 Reranker。所有最终写操作回到 Java。

**我展示：** `docs/architecture/SYSTEM_ARCHITECTURE.md` 的总览图。

**面试官应看到：** Spring Boot、MySQL、Redis、Kafka、Agent、pgvector 和监控之间的真实调用关系。

## 1:00–2:00 小程序用户流程

**我点击：**

1. 登录页使用演示账号登录。
2. 首页打开商品页，展示真实商品列表。
3. 进入“我的订单”，打开一条订单和物流详情。
4. 进入“我的 → 收货地址”，展示服务端列表；新增或编辑地址、选择省市区、设默认后重新进入页面。
5. 进入“设置 → 意见反馈”，提交一条简短建议并展示服务端返回的反馈编号。

**我说：**

> 登录后所有接口携带 JWT。地址的用户 ID 不由前端传入，服务端按 `id + user_id` 校验所有权；默认地址由事务和数据库唯一索引共同保证。反馈进入 MySQL，后台查询接口要求管理员身份。

**面试官应看到：** 页面数据来自真实 REST API，刷新后仍存在。

## 2:00–3:00 售后与 AI 客服

**我点击：**

1. 从已收货订单发起售后。
2. 选择原因、填写描述，展示上传凭证入口。
3. 提交后进入工单/客服会话。
4. 发送政策咨询，展示 AI 回复、引用或人工降级状态。
5. 打开历史会话，证明消息已持久化。

**我说：**

> 售后申请在一个 MySQL 事务中写工单与 Outbox。Outbox 定时发布 Kafka 事件，Consumer 用 Redis 做事件认领和过期接管。Agent 同时评估政策与凭证，再经过确定性 Gate。模型不可用、政策不可信或证据不足时，系统会请求补证或转人工。

**面试官应看到：** AI 异常不会让页面崩溃，消息与会话终态仍能查询。

## 3:00–4:00 Java 后端设计

**我展示：**

- `AfterSalesServiceImpl`：订单归属、工单状态与事务。
- `AfterSalesReviewEventServiceImpl`：Outbox 发布、重试与失败状态。
- `ShippingAddressServiceImpl` / `ShippingAddressMapper`：用户隔离与默认地址。
- `AgentGatewayServiceImpl`：Agent HTTP/SSE 网关。

**我说：**

> Java 拥有业务最终状态。Controller 从认证上下文解析用户，Service 负责事务和状态机，Mapper 对关键资源查询显式带用户或商家范围。Agent 只能调用注册工具，审核结果还要经过 Java 的版本与幂等校验。

**面试官应看到：** 技术亮点可以落到具体源码，而不是只讲架构名词。

## 4:00–4:30 稳定性与可观测性

**我展示：** Prometheus Targets、Grafana Agent Overview 和一段带 Trace ID 的日志。

**我说：**

> Java、Agent 和 Review Consumer 都暴露指标。面板关注请求延迟、错误、RAG 降级、Outbox 发布、DLQ 与人工接管。失败链路使用有限重试，超过边界后转人工，避免无限重试放大故障。

**面试官应看到：** 三个采集目标在线，监控对应真实服务。

## 备用追问入口

- 为什么不用模型直接改工单：最终状态必须可验证、可幂等、可审计。
- 为什么需要 Outbox：避免数据库提交成功而 Kafka 发送失败造成事件丢失。
- Redis 挂了怎么办：Consumer 有本地退化路径，但正式可靠性判断需说明边界；业务事实仍在 MySQL。
- RAG 为什么还要 Reranker：Dense/Keyword 先提高召回，Reranker 再优化候选顺序；正式审核对降级检索失败关闭。
- 为什么地址默认要数据库约束：事务逻辑覆盖正常路径，唯一索引处理并发竞争。
