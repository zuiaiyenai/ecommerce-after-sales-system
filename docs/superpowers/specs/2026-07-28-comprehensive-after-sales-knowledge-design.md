# 全品类售后知识库版本化重构设计

## 1. 背景与目标

当前 PostgreSQL 售后知识库包含 30 篇已发布文档和 30 个有效向量 Chunk。现有知识主要覆盖数码、手机和耳机，缺少服装、鞋靴、日用和食品的品类规则；部分政策、证据要求和 FAQ 之间存在重复或口径不一致；商品实际中文品类与知识库英文标准值也会导致检索退化到 `category_relaxed`。

本次重构面向演示商家 `MERCHANT_DEMO`，目标是：

- 覆盖当前商品目录中的数码、服装、鞋靴、日用和食品；
- 建立统一、可组合的售后政策、品类例外、场景证据和安全边界；
- 让复杂问题能够通过 Agentic RAG 分别召回政策、证据、时效和排除条件；
- 保持 Java 对知识发布生命周期和售后业务状态的控制；
- 使用 revision 版本化升级，不直接覆盖当前可用的 published revision；
- 保证未来数据库重建时不会从乱码种子重新生成错误知识。

## 2. 统一演示商家规则

本次不声明真实平台或法律承诺，统一采用项目演示商家规则：

- 7 天无理由退货；
- 商品破损在签收后 7 天内申请；
- 功能或质量问题在签收后 15 天内申请；
- 经核实属于质量问题、错发、少发或运输破损时，合理退货运费由商家承担；
- 食品拆封、耗材拆封使用、明显穿着或洗涤、影响二次销售等情况适用相应品类排除条件；
- AI 只提供政策解释、补证引导、初审建议和人工转接判断；
- 退款、拒绝、换货、补发以及售后状态流转始终由 Java 业务层决定。

## 3. 知识分层

### 3.1 商家统一政策层

可信政策使用 `after_sales_policy` 等受控政策来源，负责定义：

- 申请时效；
- 退款、退货退款、换货、补发和仅退款边界；
- 运费承担；
- 通用排除条件；
- 人工复核条件。

计划文档：

1. 售后申请时效与处理方式总则
2. 7 天无理由退货规则
3. 商品破损退换货规则
4. 功能及质量问题退换货规则
5. 换货与二次质量问题规则
6. 仅退款适用边界
7. 退货运费承担规则
8. 退款到账与售后处理时效

### 3.2 品类规则层

品类规则只描述该品类的特殊判定和排除条件，不复制完整通用政策。

计划文档：

1. 数码商品通用质量问题规则
2. 手机充电、开机、屏幕和电池异常
3. 耳机声音、连接、续航和降噪异常
4. 服装尺码、色差、开线、破洞和洗涤边界
5. 鞋靴尺码、开胶、断底、脱线和穿着痕迹
6. 日用品通用破损、缺件和使用边界
7. 相纸等耗材的拆封、污染、数量和打印质量问题
8. 食品包装破损、漏气、临期和变质规则
9. 食品口味不符、主观不喜欢与质量问题的区别
10. 特殊商品影响二次销售的排除条件

### 3.3 场景与证据层

证据知识使用 `scene_evidence`，只说明信息与凭证要求，不单独决定业务结果。

计划文档：

1. 商品破损证据要求
2. 功能异常证据要求
3. 异响、声音类问题证据要求
4. 充电与续航问题证据要求
5. 尺码、色差和外观差异证据要求
6. 错发少发证据要求
7. 食品安全及包装异常证据要求
8. 包装破损但商品完好的处理规则
9. 显示签收但未收到的核验规则
10. 退回商品完整性检查要求
11. 图片、视频和描述不一致的人工复核规则

### 3.4 商品判定知识层

`product_knowledge` 只描述可能的质量问题现象，不能单独作为退款或审核通过依据。

计划文档：

1. 手机常见质量问题判定
2. 耳机常见质量问题判定
3. 服装常见质量问题判定
4. 鞋靴常见质量问题判定
5. 日用耗材与食品常见问题判定

### 3.5 FAQ、话术与安全边界层

FAQ、话术和 guideline 负责解释、补证和转人工，不得覆盖政策结论。

计划文档：

1. 如何判断是否仍在售后时效内
2. 退款多久到账
3. 售后审核需要多久
4. 为什么需要补充图片或视频
5. 通用补证话术
6. 功能异常补充描述话术
7. 自动转人工边界
8. AI 售后建议权限边界

重构完成后预计约 42 篇知识文档、65 至 90 个结构化 Chunk。实际 Chunk 数由结构化分块器根据标题层级和 token 大小确定，不通过人为拆碎内容追求数量。

## 4. 规则优先级

发生内容交叉时，按以下顺序解释：

1. 品类排除条件；
2. 品类专属规则；
3. 商家统一政策；
4. 场景证据要求；
5. FAQ 和话术。

低层文档不得修改高层政策。商品判定知识只能说明问题现象是否值得进入售后核验，不能直接给出退款、换货或拒绝结论。

## 5. 文档内容契约

每篇政策或品类规则至少包含适用的以下章节：

- 适用范围；
- 已知事实与需要查询的业务事实；
- 申请时效；
- 必需信息；
- 必需证据；
- 建议证据；
- 排除条件；
- 可建议的处理方式；
- 必须人工复核的情况；
- AI 权限边界。

知识内容禁止包含：

- AI 直接退款、拒绝或修改售后状态；
- 未配置的固定赔偿金额；
- 没有证据或订单事实支持的责任结论；
- “一定通过”“保证退款”等承诺；
- 针对单个截图、单个商品记录或单条测试问题的一次性规则。

## 6. 元数据规范

### 6.1 标准值

品类使用：

- `digital`
- `phone`
- `headphone`
- `apparel`
- `shoes`
- `daily`
- `food`

主要场景统一使用：

- `damage`
- `quality_issue`
- `package_damage`
- `wrong_or_missing_items`
- `logistics_issue`
- `return`
- `exchange`
- `refund_only`
- `return_shipping`
- `refund_progress`
- `progress_query`
- `evidence_requirement`
- `human_handoff`
- `review`

主要意图统一使用：

- `refund`
- `exchange`
- `reissue`
- `refund_or_reissue`
- `evidence_requirement`
- `quality_standard`
- `policy_explanation`
- `ask_missing_evidence`
- `guardrail`

### 6.2 兼容要求

- 订单中的“数码、服装、鞋靴、日用、食品”在进入 RAG 硬过滤前转换为标准品类；
- 手机和耳机的子品类识别使用可复用的标准化分类，不为单个商品 ID 写规则；
- 首次检索、LLM 改写后的 Multi-Query 检索和所有召回通道共用同一过滤结果；
- 常规查询应保持 `filter_level=strict`；
- `category_relaxed` 仅作为无法严格命中的降级路径，不作为正常命中方式。

### 6.3 版本与有效期

- 新政策版本使用 `demo-policy-v2.0`；
- 政策类文档写入明确的 `valid_from`；
- 当前演示规则没有预设失效时间，`valid_to` 可以为空；
- 所有文档补充用于关键词召回和审计的 tags；
- FAQ、话术和商品知识不标记为可信政策；
- 只有受控政策来源可以参与高风险审核建议。

## 7. 现有文档处理

- 保留仍有独立价值的文档 ID 和稳定 `source_code`；
- 通过新 revision 改写核心文档；
- 将基础政策和细分规则中的重复段落收敛为同一口径；
- 将多个过细的手机、耳机规则合并为结构化品类文档；
- 被新文档覆盖的旧知识先软停用，不物理删除；
- 新 revision 发布成功前继续使用旧 `published_revision`；
- 新版本完成 embedding 与检索验收后再成为当前发布版本。

## 8. 发布与失败恢复

### 8.1 发布路径

- 开始前只读导出当前文档、revision、published revision 和 Chunk，形成可恢复快照；
- 现有文档通过 Java 知识管理接口进入：
  `PUBLISHED → PROCESSING → REVIEW_REQUIRED → PUBLISHING → PUBLISHED`；
- 新文档通过临时 UTF-8 Markdown 导入；
- 解析和分类完成后检查草稿 Chunk 与元数据；
- 发布完成并验证后删除一次性临时导入文件；
- 修复仓库内长期保留的乱码知识种子，确保新环境可以正确初始化。

### 8.2 安全约束

- 不重建 PostgreSQL 数据卷；
- 不执行 `docker compose down -v`；
- 不批量删除知识；
- 不在 embedding 失败时切换 published revision；
- 单篇失败不阻断其他已发布知识；
- 服务启动失败只检查一次，不循环重试；
- 不输出 API Key、数据库密码或其他凭据。

## 9. 验收设计

### 9.1 数据完整性

- 所有启用文档存在 published revision；
- 所有 published revision 至少有一个有效向量 Chunk；
- 没有重复的 `(document_id, revision, chunk_index)`；
- 文档与 Chunk 的品类、场景、意图、版本和来源元数据一致；
- 软停用文档不参与检索。

### 9.2 检索覆盖

真实用例至少覆盖：

- 每个品类的正常质量问题；
- 每个品类的无理由退货和排除条件；
- 破损、错发、少发和物流未收到；
- 证据充分和证据不足；
- 政策、证据、时效和排除条件组成的复杂问题；
- 用户描述与图片不一致；
- 超时、食品拆封、耗材使用、穿着或洗涤痕迹等反例。

### 9.3 运行标准

- 正常链路为 `hybrid_reranked` 或 `multi_query_reranked`；
- 不出现 `lexical_fallback_after_embedding_error`；
- 不出现 `hybrid_rrf_degraded`；
- 当前商品品类能够在 `strict` 层命中；
- 复杂问题可以覆盖政策、证据、时效和排除条件；
- 证据不足时不自动建议通过；
- 食品拆封、耗材使用、穿着痕迹等排除场景不会被描述成无条件支持；
- LLM 候选查询必须保留商品、问题和用户诉求事实；
- Java 仍是售后状态和最终业务结果的唯一事实来源。

## 10. 非目标

本次不包括：

- 接入真实电商平台法规或承诺；
- 修改订单、售后工单或聊天状态机；
- 让 Python 或 LLM 直接写入 MySQL 业务状态；
- 建立新的数据库或检索技术栈；
- 为不存在的商品品类提前编写大量低价值规则；
- 调低可信阈值以掩盖知识覆盖不足。
